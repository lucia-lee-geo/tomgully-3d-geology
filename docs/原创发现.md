# 原创发现：三维地质建模中的「静默失败」与可验证陷阱

> 本文是本项目在真实数据上踩到、并逐条验证过的坑。每条均可复现，附证据与复现方法。
> 原则：**可验证的讲清楚，模棱两可的讲清边界，一切基于事实。**

---

## 1. 数据治理「静默失败」：数值列被声明为 TEXT

**现象**：在 NTGS 区域钻孔库（GPKG）中，`Depth_From / Au_ppm / Longitude / Latitude` 等
数值列的 SQL 声明类型均为 TEXT。执行：

```sql
SELECT COUNT(*) FROM assay_nth_governed
WHERE Longitude BETWEEN 130.95 AND 132.25;   -- 返回 0 行！
```

**根因**：TEXT 列按字典序比较，`'131.5'` 与数值 `130.95` 的比较不符合直觉，静默返回空集，
**没有任何报错**——这是最危险的一类错误：结果「看起来正常」（0 行也可以是合法结果），
却悄悄漏掉了全部数据。

**证据**：改 `CAST(Longitude AS REAL)` 后同一查询返回 **718,345 行**。

**教训**：下游脚本对数值列必须显式 `CAST(... AS REAL)`；治理阶段应修正列型，而非在查询里打补丁。

## 2. gstlearn 三维空间陷阱：`defineDefaultSpaceRnT` 建的是 RN(n+1)

**现象**：调用 `gstlearn.defineDefaultSpaceRnT(3)` 意图建立三维空间，实测建出的是 RN(4)，
变差函数/克里金维度错误。

**根因**：该函数模板下标从 0 起，`defineDefaultSpaceRnT(n)` 实际建 RN(n+1)。

**正解**：
```python
gst.setDefaultSpace(gst.SpaceRN.create(3))   # 正确三维
```

**证据**：`getDefaultSpaceDimension()` 实测前者返回 4、后者返回 3；用错误空间构造的
VarioParam `ndim=4`。本项目在双环境（Windows py3.11 / WSL py3.14）复现一致。

## 3. 文件名 ≠ 真分辨率：`glo30` 实为 8 角秒

**现象**：一张名为 `dem_copernicus_glo30_pc.tif` 的 DEM 被当作用 30 m 分辨率使用。

**根因**：文件名的 `glo30` 是**产品系列名**，不代表该文件真实分辨率。

**证据**：`gdalinfo` / `rasterio` 实测该文件像素 = 8 角秒（≈241 m），与 30 m（1 角秒）差 8 倍。
孔口高程采样精度因此受限。

**教训**：分辨率必须读栅格元数据（`ds.res` / geotransform），不能信文件名。

## 4. 垂直基准 986 m 落差：本地 RL vs 海平面 DEM

**现象**：公司报告孔口「RL（Reduced Level）」≈ 1002 m，而 Copernicus DEM 在同一位置给 ~16 m。

**根因**：矿区常用**本地基准**（Reduced Level，人为设定），与海平面高程（AHD/EGM）不是一回事。
「From Orig → From AMG」的坐标转换只改了水平基准，RL 仍是本地值。

**证据**：MLN1058 孔口 `MGA_RL=1002.235`，Copernicus GLO-30 同点 = 16.25 m，差 ≈986 m。
若混用，矿体会「悬浮」在近千米高空。

**教训**：多源高程必须先对齐垂直基准，再做三维建模。

## 5. 空间偏移 1.2 km：「Toms Gully」钻探 ≠ 「Tom's Gully」矿床

**现象**：MLN1058 公司报告标注「Toms Gully」的岩性钻探（TGDDH 34 孔）位于官方矿床点
西南约 1.2 km，与含 Au 的浅层孔（TGP）不重叠。

**证据**：
- 官方矿床点（NTGS mineral_deposits / reserves_resources）：131.5608°E, −12.831°S → MGA (777967, 8580173)
- TGDDH001 孔口（MLN1058 collar `MGA94_52`）：MGA (777327, 8579199) → 131.555°E, −12.840°S
- 二者直线距离 ≈ 1,166 m；TGDDH 区域在 DIP001 中 **0** 条 Au 化验，TGP 区域 584 条。

**根因**：公司报告用「Toms Gully」指代整个矿权/项目区，而非矿床本体；不同数据集的空间
归属必须用**官方坐标**交叉核对，不能只信文件名/项目名。

**教训**：「数据最完整」不等于「数据同址」——本项目因此把**岩性建模**（TGDDH）与
**品位/储量估算**（TGP）分开处理，并各自标注位置与边界。

## 6. 政府开放数据 vs 公司私有数据的边界

**现象**：基于公开浅层 TGP 数据（0–60 m）只能估出 ~1.3 万 oz，官方 JORC 2010 为 ~14 万 oz。

**根因**：深部资源定义钻探（TGDDH 至 840 m）的 Au 化验在**公司报告 PDF** 内，政府开放库
（DIP001）未收录其化验；公开数据天然只有「浅层 + 老孔」。

**证据**：DIP001 `assay_nth_governed` 中 Tom's Gully 区域 Au 样段深度范围 0–60 m；
官方 2010 资源量（321 kt @ 8.9 g/t）由 2009–2010 深钻支撑。

**边界**：开源 + 开放数据能复现**方法**并给出**量级**，但**全矿床资源**仍需公司化验 +
合资格人（Competent Person）签字。脚本不代判。
